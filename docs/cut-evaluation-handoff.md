# ITDA Studio 컷 연출 평가 구현 인수인계

배치 생성된 컷마다 **Fidelity(객체 무결성), BF(브랜드 적합도), TQ(기술적 품질)**를 평가한다. 종합 모델이 컷별 채택 가능성을 계산해 자동 채택, 사용자 검토, 자동 제외로 분류한다. 개별 모듈은 점수와 평가 가능 상태를 종합 모델에 전달한다.

## 평가 항목

| 항목 | 입력 | 평가 방식 | 점수 |
| --- | --- | --- | --- |
| Fidelity | 원본 제품 이미지 + 생성 컷 | 양쪽을 rembg 처리하고 고정 DINOv2 특징을 결합해 예측층에 입력 | `100 × 모델 출력` |
| BF | 생성 컷 + 선택한 브랜드 Pool의 대표 벡터 4개 | 긍정/부정 × 색상/grayscale 평균 방향과 집중도로 평가 | `clip(50 + 50E+ − 50E−, 0, 100)` |
| TQ | 원본 제품 이미지 + 생성 컷 | 결과의 채도·음영 대비·흐림을 CV로 측정하고 원본 제품 특성을 참고해 심각도 산출 | `100 × (1 − 심각도)` |

Fidelity 모델 출력과 TQ 심각도는 0~1 범위다. BF는 아래의 대표 벡터·집중도 공식을 사용한다. 구매전환과 CTR은 고객사의 실제 이용·성과 데이터를 별도로 검증할 과제로 둔다. VMD 미감 평가는 TQ로 대체했다. GPT Decisions API로 점수를 산출한 뒤 후보정하는 방식은 보류했다.

### Fidelity

#### 현재 구현과 한계

- `evaluator/fidelity/`가 추론·학습·피드백을 담당하고, `dataset_collector/`가 이미지 쌍과 라벨을 생성·보관한다.
- 데이터셋의 평가와 실제 추론 모두 원본·결과에 rembg U2Net을 적용한다. EXIF 방향을 보정하고 투명 영역을 중립 회색에 합성한 RGB를 고정 DINOv2 Small로 인코딩한다. 원본 CLS와 결과 CLS를 순서대로 연결한 768차원 벡터를 사용한다. 인코더 revision과 전처리 설정을 모델에 기록·검증하고 이미지 특징을 캐시한다.
- rembg는 특정 의뢰 제품을 식별하지 않으며 복잡한 컷의 다른 물체, 가림, 마스크 실패를 정확하게 구분하지 못할 수 있다. 추론 API는 평가 가능 여부를 별도로 판정하지 않는다. 제품 검출·분할과 시점·가림 변화에 대한 검증은 후속 과제다.
- 새 학습 코드는 표준화된 연결 특징의 선형 결합에 sigmoid를 적용하고 이진 교차 엔트로피와 L2 정규화로 학습한다. 라벨은 `0`, `0.5`, `1`만 허용한다. `0.5`는 경계 사례의 소프트 목표다. 출력은 연속값이며 100을 곱해 0~100 점수로 반환한다. 이 값은 검증된 실제 합격 확률이 아니다.
- 기본 모델 경로 `evaluator/models/fidelity-v2.npz`는 기존 연속 Decisions 확률 라벨 413건으로 sigmoid와 평균제곱오차를 사용해 학습한 모델이다. 새 교차 엔트로피 학습 코드를 적용하거나 라벨을 수정했다고 이 파일이나 서버 모델이 자동 재학습·교체되지는 않는다. 당시 test 62건의 MAE는 21.27점이며, 새 라벨 기준 성능으로 해석할 수 없다.

#### 데이터셋 생성과 판정

데이터셋은 `dataset_collector/datasets/<이름>/`에 기록한다. 원본과 생성 결과, 배경 제거된 이미지, 생성 프롬프트·목표·trial·모델 정보 및 Fidelity 라벨을 보존한다. 제품 단위로 train/validation/test를 분리하고 동일 이미지의 분할 간 중복을 검사한다.

- 이미지당 기본 8회 생성한다. 기존 생성 프리셋을 무작위로 선택하고 목표 Fidelity의 네 구간을 구간별 두 번씩 사용한다. 각 trial마다 독립적으로 50% 확률로 앞선 지시를 무시하고 제품 형태·구조를 원본과 다르게 만들라는 지시를 끝에 추가한다. 목표와 추가 지시는 결과 품질이나 라벨 분포를 보장하지 않는다.
- 생성 후 두 이미지에서 배경을 제거하고 OpenAI Decisions의 `choice` 질문으로 제품 보존 양호·경계·실패를 선택한다. `good=1`, `borderline=0.5`, `failed=0`이며 비교 불가와 명시적 거절도 0으로 처리한다. 거절은 별도 출처로 기록하며, 누락·잘못된 응답은 오류로 처리한다. 기존 필드명 `fidelity.probability`에는 호환성을 위해 이 이산 라벨을 저장한다. 새 값은 확률이 아니다.
- 생성 목표나 50% 변형 여부를 평가 API에 전달하지 않는다. 모델 라벨은 자동 판단이므로 사람의 검수 기준과 일치하는지 확인하고 필요하면 수정한다. 기존 연속 라벨 데이터셋은 새 학습에 맞게 수정해야 한다.

```bash
python -m dataset_collector create fidelity-v3
python -m dataset_collector generate fidelity-v3 /path/to/input --trials 8
python -m dataset_collector generate fidelity-v3 /path/to/input --trials 8 --resume
```

`--resume`은 동일 입력·trial 설정의 저장된 생성 결과를 건너뛰고 미완료 전처리·평가를 재시도한다. 처음 `--seed`를 지정했다면 같은 값을 사용한다. 이미지가 변경되거나 같은 제품·trial 기록이 중복되면 중단한다. 이전 결과를 재사용해 다시 평가하려면 `python -m dataset_collector reprocess <기존> <새데이터셋>`을 사용한다. 자세한 사용법은 `dataset_collector/README.md`를 참조한다.

#### 학습과 검증

```bash
python -m evaluator.fidelity.train fidelity-v3 --output evaluator/models/fidelity-v3-logistic.npz
```

라벨이 0, 0.5, 1 이외이면 학습 전에 오류를 반환한다. 학습 분할에서만 특징 평균·표준편차를 구하고, 검증 MAE로 정규화 계수를 선택해 train/validation/test의 MAE·RMSE와 모델 메타데이터를 `.npz`에 저장한다. 동일 제품은 서로 다른 분할에 들어가지 않는다. 출력 파일은 기존 파일과 겹칠 수 없다. 라벨 품질, 클래스별 성능과 실제 사용자 판단에 대한 일반화는 별도로 검증해야 한다.

#### 추론과 온라인 피드백

`POST /api/v1/cut-evaluation/fidelity/predict`는 multipart `original_image`, `generated_image`를 받아 `{"score": ..., "model_version": ...}`을 반환한다. 기본 파일은 `fidelity-v2.npz`이며 `FIDELITY_MODEL_PATH`로 변경할 수 있다. 상세 계약은 `docs/client-api.md`를 참조한다.

`POST /api/v1/cut-evaluation/fidelity/feedback`은 두 이미지와 `positive` 또는 `negative`, 부정 사유를 받는다. 종합 긍정은 Fidelity 긍정 1로, Fidelity 사유가 포함된 부정은 0으로 저장한다. Fidelity 사유가 없는 부정은 저장하지 않는다. 출처·신호를 구분하며 원본 이미지와 배경 제거 이미지를 함께 보관한다. 기본 피드백 데이터셋은 `fidelity-v2`이고 `FIDELITY_FEEDBACK_DATASET`으로 바꿀 수 있다.

저장 때마다 백그라운드 학습 조건을 확인한다. 기본적으로 학습 분할의 미처리 피드백 8건과 기존 학습 사례 최대 32건을 섞어 예측층만 갱신한다. 검증·시험 분할의 피드백은 저장하지만 학습하지 않는다. 학습 중에는 이전 모델을 사용하고 완료된 후보를 서버 재시작 없이 적용한다. 그동안 8건이 더 쌓였으면 적용 후 다음 배치를 진행한다. 검증 지표는 기록하지만 현재 자동 적용에 검증 통과 조건은 없다. 기존 v2 모델의 온라인 재현 학습은 기존 연속 라벨에 MSE를 사용하고, 새 교차 엔트로피 모델은 재현 라벨에도 교차 엔트로피를 사용한다.

온라인 상태는 기본적으로 `evaluator/models/online/<데이터셋>/state.json`과 후보 파일에 저장되며, 데이터셋과 기준 모델 경로에 연결된다. 기준 모델을 교체할 때 기존 상태와 충돌하지 않도록 `FIDELITY_ONLINE_OUTPUT_DIR`을 새 경로로 지정하고 피드백 데이터셋과 모델 메타데이터가 일치하는지 확인한다. `FIDELITY_ONLINE_BATCH_SIZE`, `FIDELITY_ONLINE_REPLAY_SIZE`로 배치 크기를 설정할 수 있다.

`/api/v1/cut-evaluation/fidelity/dashboard`에서 이미지 쌍과 점수, 실시간 분포를 확인하고 라벨을 수정할 수 있다. 대시보드 수정은 이미 학습된 모델을 자동으로 다시 학습시키지 않는다.

### BF

#### 판단 원칙과 Pool 구성

VLM 호출 없이 결과 이미지와 지정 브랜드의 대표 임베딩 4개를 비교한다. 사례별 최근접 비교 전략을 대체한다.
색상 분포와 색상을 제외한 grayscale 패턴·형태를 두 표현으로 나누어 평가한다.
이미지만으로 브랜드의 철학 자체를 확정하지 않으며 시각적 정합성을 측정한다.

- 사용자가 등록한 기준 이미지와 긍정 피드백 결과는 같은 긍정 Pool을 공유한다. 출처는 구분해 보존한다.
- BF 사유의 부정 피드백 결과는 부정 Pool에 추가한다. 다른 평가 항목만으로 제외된 이미지를 BF 부정으로 간주하지 않는다.
- 피드백 시 색상/디자인 축을 나누지 않고 긍정/부정만 받는다. 한 부정 사례에서 두 축이 각각 잘못됐다고 확정하지 않는다.
- 생성과 평가에 같은 Pool 스냅샷을 사용하는 것을 목표로 한다. Pool 미지정은 0점이 아닌 `not_applicable`이다.
- 긍정/부정 × 색상/디자인별로 하나의 평균 방향과 집중도를 저장한다. 다양한 디자인이 평균화되는 것은 브랜드 전체의 공통 성향을 평가하려는 의도에 부합한다.
- 공통성이 약한 축은 강하게 제한하지 않는다. 집중도가 낮아지면 해당 축의 점수 기여를 중립으로 줄이며, 남은 축으로 가중치를 재분배하지 않는다. 원래 사례는 수정·삭제·재집계용으로 보존하지만 예측에는 읽지 않는다.
- 채널별 파일·배치 규격을 BF에 포함할 범위와 기존 평가 근거 보존 정책은 추가 결정이 필요하다.

아래 특징·점수·로컬 API는 현재 구현이다. 원격 Supabase/R2 연동은 후속 설계이며 아직 구현되지 않았다.

#### 특징과 점수 — 현재 구현

공통 특징 코드는 `evaluator/features/appearance.py`에 위치한다.

- 색상: 공간 좌표를 사용하지 않는 8×8×8 Lab 히스토그램(512차원).
  알파로 픽셀을 가중하고 합을 1로 만든 뒤 제곱근을 취한다.
  이 벡터의 내적은 색상 분포의 Bhattacharyya affinity이다.
- 디자인: EXIF 방향 보정 → 투명 영역 중립 회색 합성 → grayscale → RGB 3채널 복제
  → 고정 DINOv2 Small CLS → L2 정규화(기본 384차원).
- 양쪽 모두 입력 이미지 전체를 사용한다. 배경 제거·제품 식별·무늬 영역 검출은 수행하지 않는다.
  제품 디자인을 평가하려면 클라이언트가 일관된 제품/무늬 크롭을 제공해야 한다.
  grayscale에도 밝기·조명·배경 정보는 남는다.

DINOv2는 기존 실행 환경을 재사용하는 초기 기준선이다. 스타일 전용으로 학습된 모델이
아니며, 색상이 다른 동일 디자인의 구별 성능은 실제 상품으로 검증해야 한다.

각 그룹 g(positive/negative), 축 a(color/design)의 단위 사례 벡터를 z_i라 하면:

```text
S[g,a] = Σ z_i                          # 합계 벡터
m[g,a] = S[g,a] / N[g]                  # 평균 벡터
b[g,a] = S[g,a] / ||S[g,a]||             # 대표 방향
c[g,a] = clip((||S[g,a]||² - N[g]) / (N[g](N[g]-1)), 0, 1)
```

N > 1일 때 c는 서로 다른 사례 쌍의 평균 cosine을 0~1로 자른 집중도다.
쌍마다 직접 비교하지 않고 합계와 개수만으로 구한다. 평균을 정규화한 방향만 저장하면
사라지는 분산 정보를 c와 `mean_norm=||m||`으로 보존한다.

- N=0: 대표 방향 없음, 집중도 0. 긍정 Pool 자체가 비어 있으면 `unavailable/no_positive_examples`.
- N=1: 집중도는 임시로 1을 사용하되 `concentration_estimated=false`와 개수를 반환한다. 한 장으로 브랜드 일관성이 검증됐다는 뜻은 아니다.
- 합계가 0에 가까우면 방향 없음·집중도 0으로 처리한다.

결과 이미지의 정규화 벡터 q와 대표 방향의 유사도는 `s[g,a]=clip(q[a]·b[g,a],0,1)`이다.
기본 축 가중치는 각각 0.5다. 집중도가 낮은 축의 가중치는 다른 축으로 넘기지 않는다.

```text
E+ = Σ_a 0.5 × c[positive,a] × (2s[positive,a] - 1)
E− = Σ_a 0.5 × c[negative,a] × s[negative,a]
BF = clip(50 + 50E+ - 50E−, 0, 100)
```

50은 중립 기준점이며 채택 가능성 50%를 뜻하지 않는다. 긍정 공통 성향과 일치하면 가점,
불일치하면 감점한다. 부정의 공통 성향과 유사하면 추가 감점한다. 부정 사례가 없으면 E−=0이다.
두 Pool의 공통성이 모두 약하면 점수는 50에 가까워진다. 긍정과 부정이 모두 강하게 비슷하면
상반된 신호가 상쇄된다. 따라서 점수만으로 충분한 판별 근거가 있다고 해석하지 않으며 축별 근거와 집중도를 함께 반환한다.

피드백은 축별 원인을 지정하지 않는다. 부정 대표의 색상·디자인은 각각 잘못됐다고 확정된 속성이 아니라
부적합 이미지들의 통계다. 축별 원인 분리 학습은 구현하지 않는다.
대표 비교로 바뀌면서 색상·디자인의 사례별 결합 관계와 드문 부정 유형은 유지되지 않으며,
개별 계열의 허용 여부보다 전체 공통 성향을 평가한다.

점수식 버전은 `prototype-concentration-v2`, 집계 버전은 `mean-pairwise-cosine-v1`이다.
기존 `joint-knn-support-v1`의 점수·임계값과 호환되지 않는다. `nearest`,
`positive_similarity`, `negative_similarity`, `top_k` 대신 `axes`, `evidence`를 반환한다.
`axes`에는 그룹별 개수와 집중도 추정 여부, 축별 유사도·집중도·가중 기여도가 들어간다.
이는 학습된 회귀 모델이나 보정된 확률이 아니다. 실제 BF 데이터로 가중치·중립점·감점 크기와 임계값을 검증해야 한다.
특히 DINOv2 임베딩의 공통 방향 성분 때문에 의미적으로 다양한 이미지의 cosine도 높을 수 있으므로,
집중도를 브랜드 정체성의 절대적인 척도로 해석하지 않는다.

예측의 벡터 읽기·집계·비교는 사례 수 N과 무관한 O(d)이다. 이미지 인코딩 비용은 별도다.
긍정·부정 사례 목록 전체를 가져오거나 정렬하지 않는다.

#### 저장과 버전 — 현재 로컬 구현

SQLite에 원본의 EXIF 방향을 보정한 RGBA PNG, 두 임베딩, 라벨, 출처를 보존한다.
중복은 정규화 PNG의 SHA-256으로 판별하며, 동일 이미지를 다시 등록하면 라벨과 출처를
갱신한다. 따라서 한 이미지가 양쪽 Pool에 동시에 존재하지 않는다.
한 요청의 사례 추가는 하나의 트랜잭션으로 처리한다. 업데이트/삭제마다 Pool 버전이 증가한다.
`pool_aggregates`에 긍정/부정의 개수와 축별 합계 벡터를 저장한다.
대표 방향·집중도는 이 고정 크기 통계에서 O(d)로 복원하며 원본 사례를 재조회하지 않는다.
추가 시 합산하고, 라벨 변경·재등록은 기존 벡터를 차감한 뒤 새 벡터를 합산하며,
삭제 시 차감한다. 사례·통계·Pool 버전을 같은 트랜잭션에서 갱신한다.
기존 DB는 통계가 없는 Pool만 최초 접근 때 전체 사례를 한 번 읽어 자동 집계한다.
집계 계산은 변경 사례당 O(d)이지만 관리 API의 전체 사례 목록 응답에는 O(N) 비용이 남는다.
조회/예측은 일관된 Pool 스냅샷을 사용한다. 예측은 `include_examples=False`로 통계만 읽는다.

`BRANDFIT_DB_PATH` 기본값: `evaluator/cache/brandfit.sqlite3`.
`BRANDFIT_ENCODER_MODEL` 기본값: `facebook/dinov2-small`.
`BRANDFIT_ENCODER_REVISION` 기본값: `main` (운영 시 commit hash 고정 권장).
실제 해석된 모델 commit, 모델 이름, 특징/전처리 버전으로 encoder signature를 생성한다.
Pool과 활성 encoder signature가 다르면 HTTP 409를 반환하므로 Pool을 다시 등록해야 한다.
모델 가중치는 최초 사용 시 로드하며 서버 시작이나 health 조회에서는 로드하지 않는다.

Pool 버전은 변경 카운터이며 과거 Pool 전체의 이력이나 과거 예측 결과를 자동 보존하지는 않는다.
과거 평가를 재현해야 하는 호출자는 반환된 버전과 임베딩 스냅샷/결과를 별도로 보관해야 한다.

#### API — 현재 로컬 구현

접두사: `/api/v1/cut-evaluation/brandfit`

| 메서드 | 경로 | 입력 |
| --- | --- | --- |
| POST | `/pools` | multipart `name`, 반복 `images`: 기준 이미지로 Pool 생성 |
| GET | `/pools/{id}` | 대표 벡터·집중도 및 사례 요약. `include_embeddings=true`이면 사례 벡터 포함. `prototypes_only=true`이면 사례 목록 없이 대표 정보만 조회 |
| POST | `/pools/{id}/references` | 반복 `images`: 긍정 Pool에 기준 이미지 추가 |
| POST | `/pools/{id}/feedback` | `feedback=positive\|negative`, 반복 `images` |
| POST | `/predict` | `brand_id`, `generated_image` |
| DELETE | `/pools/{id}/examples/{example_id}` | 사례 제거 |
| DELETE | `/pools/{id}` | Pool과 이미지·벡터 삭제 |

```bash
curl -X POST http://localhost:8000/api/v1/cut-evaluation/brandfit/pools \
  -F 'name=brand-a' -F 'images=@reference1.png' -F 'images=@reference2.png'

curl -X POST http://localhost:8000/api/v1/cut-evaluation/brandfit/predict \
  -F 'brand_id=RETURNED_brand_id' -F 'generated_image=@result.png'

curl -X POST http://localhost:8000/api/v1/cut-evaluation/brandfit/pools/RETURNED_brand_id/feedback \
  -F 'feedback=negative' -F 'images=@result.png'
```

Pool 미선택은 BF API를 호출하지 않고 종합 평가에 `bf.status=not_applicable`로 전달한다.
평가 응답의 `status`, `score`(scored일 때), `reason`(unavailable일 때)만
기존 `/api/v1/cut-evaluation/predict`의 `bf` 객체에 전달하면 된다.
기존 Fidelity 피드백 API의 `reasons=bf`는 이 Pool을 갱신하지 않는다.
클라이언트가 선택된 BF Pool ID로 위 피드백 엔드포인트를 호출해야 한다.

추가·재등록·라벨 변경·삭제의 증분 집계, 기존 DB 마이그레이션을 확인한다.

동일 스타일의 다른 색상·다른 제품, 동일 색상의 다른 스타일, 촬영 배경 변화,
긍정과 유사하지만 BF 부적합인 사례가 적절히 구별되는지 확인해야 한다.

#### 원격 브랜드 DB 연동 — 후속 설계

> DB 구조 갱신: [브랜드 임베딩 저장](brand-embedding-storage.md)을 따른다. 원격에는 브랜드별 현재 합계 벡터 4개와 사례 수·인코더 설정만 저장한다. 아래 스냅샷 보존 관련 내용은 이전 설계 배경이며 현재 요구사항에서 제외한다. image_evaluations에 fidelity/bf/tq/overall의 최신 값만 저장하고 과거 점수·진단·Pool 스냅샷은 보존하지 않는다. 실제 Python 원격 연결은 별도다.

2026-11-25에 제공된 ITDA Studio DB 구조 문서를 기준으로 한다. 운영 DB를 직접 조회해 확인한 내용은 아니다.
업무 데이터는 Supabase에, 실제 이미지 바이트는 비공개 Cloudflare R2에 있다.
원격 DB를 사례 구성과 라벨의 원본으로 삼고, 로컬 SQLite는 사례 임베딩 및 대표 통계 캐시로 전환하는 방향이다.
현재 로컬 Pool 등록/피드백 API가 원격 DB를 갱신하거나 조회하는 것은 아니다.

| 원격 테이블·필드 | BF 연동 용도 |
| --- | --- |
| `brands.id`, `workspace_id`, `deleted_at` | 지정 브랜드와 서버의 접근 범위 및 논리 삭제 확인 |
| `brand_assets.brand_id`, `asset_id`, `case_type` | 사례 연결과 positive/negative 구분 |
| `assets.id`, `workspace_id`, `status`, `deleted_at` | 같은 워크스페이스의 ready·미삭제 자산만 선택 |
| `assets.bucket`, `object_key` | R2 객체 위치. 경로를 추측해 조립하지 않고 저장된 값을 사용 |
| `assets.checksum` | 이미지 변경 감지 및 캐시 키 구성. NULL 허용 |
| `brands.lock_version` | 동시 수정 감지용. 이미지 변경이나 과거 Pool 스냅샷을 대표하는 버전은 아님 |

평가 흐름은 다음과 같이 연결한다.

1. 결과 이미지와 `brand_id`를 받는다. 워크스페이스는 요청 본문의 임의 값이 아닌 신뢰할 수 있는 서버 인증 문맥에서 결정한다.
2. 해당 범위에서 활성 브랜드와 `brand_assets`·`assets`를 조회한다. service_role은 RLS를 우회하므로 서버에서 접근 범위를 확인해야 한다.
3. 별도 동기화 경로에서 원격 사례 추가·수정·삭제·라벨 변경을 감지해 사례 임베딩 캐시와 네 대표 통계를 갱신한다. 신규·변경 이미지만 R2에서 받아 추출하고 라벨 변경은 벡터 이동만 수행한다. 삭제 사례는 통계에서 차감한다.
4. 평가 경로는 동기화가 완료된 대표 통계와 스냅샷 식별 정보만 읽는다. 전체 사례 다운로드·재집계를 매 평가마다 수행하지 않는다. 변경 통지 또는 신뢰할 수 있는 버전 확인 방식과 최신성 보장·동기화 지연 정책은 후속 구현에서 결정한다.
5. 결과 이미지의 두 임베딩을 네 대표 방향·집중도와 비교하고 사례 스냅샷 식별 정보, 인코더·점수 버전을 반환한다.

캐시 키에는 원격 저장소 식별자, 워크스페이스, 자산 ID, 이미지 콘텐츠 버전, encoder signature를 포함한다.
체크섬이 없으면 R2 ETag 등 객체 변경 정보를 확인하는 방안을 구현 시 정해야 한다.
현재 스키마에 임베딩 컬럼은 없으며, 원격 임베딩 테이블 추가는 확정되지 않았다.

피드백의 positive/negative는 원격 `brand_assets.case_type`에 반영된 상태를 따라야 한다.
현재 스키마의 `(brand_id, asset_id)` PK는 한 자산을 같은 브랜드의 양쪽 Pool에 중복 등록하지 못하게 한다.
다만 `case_type IS NULL`의 의미는 제공 문서에 명시되지 않았다.
이를 기준 이미지로 보아 긍정 Pool에 포함할지는 **미확정**이며, 자동으로 긍정/부정에 배정하지 않는다.

브라우저의 `/api/assets/{asset_id}`는 앱 세션과 접근 범위 확인을 거치는 스트리밍 경로다.
Python 평가 서버에서 바로 호출 가능하다고 가정하지 않는다. 서버용 R2 접근 또는 인증된 내부 이미지 전달 경로를 마련해야 한다.
접속 자격 증명·환경 설정은 별도 연결 작업이며, 비밀키는 클라이언트에 전달하지 않는다.

생성 시점과 평가 시점 사이 Pool 변경을 감지하려면 사례 목록·라벨·이미지 버전의 스냅샷 식별자가 필요하다.
`brands.lock_version`만으로 같은 Pool 사용을 보장하지 않는다. 과거 스냅샷 보존과 요청 계약은 후속 구현에서 정한다.
또한 현재 `image_evaluations`에는 BF 항목 구분·브랜드·Pool 스냅샷을 명시하는 필드가 없으므로,
BF 결과를 이 테이블에 저장하는 매핑과 스키마 확장은 별도 결정이 필요하다.

### TQ

허용 범위에서는 심각도를 0으로 두고, 극단적인 경우에만 감점한다. CV 측정과 심각도 변환을 분리한다.

| 진단 항목 | CV 측정 후보 | 해석 기준 |
| --- | --- | --- |
| 과도한 채도 | HSV 채도 분포와 고채도 픽셀 비율 | 원래 선명한 제품과 의도적인 강조색을 고려한다. |
| 과도한 밝기·음영 대비 | 휘도 분포, 극단 휘도 비율, 국소 대비 | 흰 벽·검은 제품과 노출로 인한 제품 디테일 손실을 구분한다. |
| 과도한 흐림 | Laplacian 분산, 경사도 등 고주파 성분 | 주제품의 선명도를 우선 측정하고, 의도적인 배경 흐림과 입력 해상도를 고려한다. |

초기에는 고정된 허용 범위와 감점 곡선을 사용한다. 세 심각도를 결합하는 초기 후보는 최댓값이다. 실제 컷으로 임계값과 결합 방식을 검증한다. 이후 학습 모델로 TQ 제외 가능성을 추정한다면, 이를 물리적 결함량과 구분해서 해석한다.

## 종합 판단과 피드백

- 종합 logistic regression에는 Fidelity·BF·TQ 점수와 각 항목의 적용·평가 가능 상태를 입력하는 구성을 우선 검증한다. 출력에 100을 곱한 값은 사용자 채택 가능성을 나타낸다. 낮은 임계값 아래는 자동 제외, 높은 임계값 이상은 자동 채택, 그 사이는 사용자 검토로 보낸다. 초기 모델과 임계값은 검수 데이터로 정한다.
- BF 미적용과 분할·비교 실패를 결측 사유별로 보존한다. BF에 임의의 0점을 넣으면 풀 미지정이 브랜드 불일치로 해석된다. 적용 여부를 입력으로 명시하거나 BF 적용 여부에 따라 종합 모델을 나누는 방식을 비교한다.
- 사용자는 컷마다 적합 또는 부적합을 선택한다. 부적합 사유는 Fidelity·BF·TQ 중 하나 이상을 선택하며 하위 항목 입력은 받지 않는다.

| 사용자 판단 | 종합 모델 | Fidelity | BF | TQ |
| --- | --- | --- | --- | --- |
| 적합 | 명시적 긍정 | 종합 긍정을 Fidelity 라벨 1로 저장 | 지정 Pool의 긍정 검수 사례에 추가 | CV 측정 벡터를 약한 긍정 후보로 저장 |
| 부적합 | 명시적 부정 한 건 | Fidelity 선택 시 비교 특징을 부정 사례로 저장 | BF 선택 시 지정 Pool의 부정 검수 사례에 추가 | TQ 선택 시 전체 CV 측정 벡터를 부정 사례로 저장 |

선택되지 않은 제외 사유는 미라벨로 유지한다. Fidelity는 종합 긍정을 1로 학습하되 출처를 구분한다. TQ의 하위 원인은 사용자 피드백에 없으므로, TQ 부정 한 건에서 채도·휘도·흐림 중 특정 원인을 확정할 수 없다. 누적 측정 벡터로 허용 범위·감점 함수 또는 TQ 제외 예측 모델을 조정한다.

## 실행과 검증

- Next.js가 Pool 관리, 평가 작업 등록, 결과 표시, 사용자 검수를 담당한다. Python 작업자는 제품 분할, DINOv2 특징 추출, OpenCV 측정, 점수 추론·학습을 담당하는 구성을 권장한다. 배치 평가는 비동기로 처리하고 컷별 결과를 저장한다.
- 결과에는 원본·결과 식별자, 프로젝트와 생성 조건, Pool 버전, 전처리·모델 버전, 비교 특징·CV 측정값, 항목별 점수·평가 상태, 종합 점수와 사용자 판단·사유를 연결한다.
- 피드백은 학습용으로 저장한다. Fidelity 온라인 학습은 기존 사례 일부를 섞어 후보를 자동 적용하며, 검증 통과 여부에 따른 적용 제한은 후속 과제다. 회색지대 사례에 편중되지 않도록 자동 채택·제외 결과도 일부 표본 검수한다.
- Fidelity는 제품 단위로 학습셋과 검증셋을 나누고, 정상적인 시점·가림 변화와 실제 부품 변형을 모두 포함한다. BF는 같은 컷에 서로 다른 Pool을 적용했을 때 점수가 적절히 달라지는지 확인한다. TQ는 의도적인 밝기·채도·배경 흐림을 결함과 구분하는지 확인한다.
- 관제 성능은 자동 채택 컷의 불량 비율, 정상 컷의 자동 제외 비율, 사용자 검토 비율로 확인한다. DINOv2 S/B의 실제 메모리·처리 시간은 초기 16GB VRAM 환경에서 해상도·배치 크기·생성 모델 동시 구동 조건별로 측정한다.
